# FND-01 — Multi-tenant product foundation

**Status:** Core complete — platform tenant-user administration extension specified; implementation pending
**Feature source:** `FEATURES.md` section FND-01
**Owner:** Primary agent

## Problem and outcome

The product needs a safe reusable boundary between logistics companies before any business module is added. FND-01 establishes a deployable Next.js frontend, NestJS backend, and Prisma/PostgreSQL persistence layer in which a Platform Admin can provision a tenant, invite its first owner, inspect platform-level health, deactivate or reactivate the tenant, and prove that tenant-owned data cannot cross that boundary.

The completed slice provides:

- a platform tenant registry and protected Platform Admin console;
- atomic, idempotent tenant provisioning with configurable bootstrap defaults;
- a minimal authentication/session and owner-invitation kernel required to exercise tenancy;
- server-derived active-tenant context and a multi-tenant switcher;
- a setup checklist, branding/configuration summary, default legal entity, and a deliberately non-business `tenant probe` resource used to prove isolation;
- PostgreSQL-backed audit events, invitation-delivery events, jobs, platform alerts, and a reconciled platform health report;
- local production-style deployment and automated isolation verification against the central PostgreSQL service.

FND-01 is not the general identity/authorization feature. FND-02 will add the full role catalogue, hierarchical scopes, MFA hooks, sensitive-field permissions, account administration, and external portals without weakening this foundation.

## In scope

1. Bootstrap the repository layout from `docs/ARCHITECTURE.md`: independently buildable Next.js and NestJS applications plus shared domain, database, authentication, configuration, UI, and observability packages where the implementation needs them.
2. Provision, read, list, deactivate, and reactivate tenants through Platform Admin-only APIs and UI.
3. Capture every tenant field listed in FND-01, validate it, and show deterministic loading, success, validation, conflict, error, and retry states. Registered addresses are pincode-first: the server resolves and snapshots city/state from a versioned PostgreSQL postal directory instead of asking the user to type them in the normal flow.
4. Atomically create tenant defaults, one default legal entity and matching canonical `LEGAL_ENTITY` organization root/scope/closure, setup-checklist rows, the first Tenant Owner membership/invitation, an invitation-delivery event, and audit evidence.
5. Minimal local authentication for a seeded Platform Admin and accepted Tenant Owner invitations, using hashed passwords and opaque database-backed sessions.
6. Resolve active tenant exclusively from the authenticated server session and membership. Never authorize with a tenant ID supplied in a query, path, body, cookie, or frontend state alone.
7. Tenant switcher for a user with at least two active memberships and tenant-specific UI state invalidation on switch.
8. Tenant setup overview and configuration/branding summary. The checklist links future areas but does not implement those modules.
9. Tenant-scoped `tenant probe` CRUD/list/export/event/document/report behavior solely as an isolation harness. The probe is not presented as a logistics business feature.
10. Platform health report and persisted operational alerts described below.
11. UTC timestamps, tenant-timezone rendering, optimistic versions, validation, audit, structured logs, correlation IDs, security headers, CSRF protection, and safe error envelopes.
12. Forward migration, deterministic development/E2E seed, clean-test-database migration, local deploy scripts, readiness endpoints, and all required automated tests.
13. From a tenant detail page, Platform Admin can inspect every membership in that tenant, understand activation and onboarding completeness, and perform an explicitly audited operational intervention: update the tenant-specific membership profile/access, rotate an invitation, suspend/reactivate the membership, or reset sessions/MFA. This extension depends on FND-02 identity tables and authorization invariants and never creates an impersonated tenant session.

## Out of scope

- Tenant-self-service user administration, the role/capability catalogue, hierarchical resource scopes, MFA authentication, password reset, SSO, vendor/driver/client portals, and fine-grained permission evaluation remain owned by FND-02. The platform tenant-user administration extension only exposes an explicitly platform-authorized operational surface over those canonical FND-02 records; it does not duplicate their domain rules.
- Organization hierarchy, employee masters, and user-created legal entities beyond the single bootstrap legal entity (MST-01).
- Clients, vendors, vehicles, drivers, contracts, operations, documents, billing, or other logistics transaction models.
- Customer-configurable role editing or no-code branding/configuration screens (CFG-01). FND-01 only reads bootstrap configuration and renders its branding.
- General user email, password-reset email, SMS, and WhatsApp providers. INT-01 now supplies an optional AWS SES adapter for new-tenant owner activation; local/provider-disabled mode retains the audited one-time replacement-link flow.
- WebSockets. Because the feature introduces no websocket endpoint, the isolation criterion is satisfied by proving there is no websocket transport and by applying the same tenant-context contract to the event-delivery abstraction.
- Redis, message brokers, external queues, object storage, Mailpit, a separate worker, or a project-specific PostgreSQL container.
- Precise per-table disk attribution. The report exposes current project database size and tenant-owned row counts; a tenant storage estimate is explicitly labelled as an estimate if implemented.

## Actors, permissions, and scopes

FND-01 uses three fixed bootstrap capabilities. They are centralized policy constants, not scattered UI role checks, so FND-02 can extend them.

| Actor/capability                          | Allowed scope                                                                  | Sensitive fields/actions                                                                                                          | Denied behavior                                                                                                                                       |
| ----------------------------------------- | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Platform Admin / `platform:admin`         | Global tenant registry, provisioning, platform report/alerts, tenant lifecycle | Can view tax identifier, invitation email, delivery status, health, deactivate/reactivate, and copy the one-time local invite URL | Cannot read tenant probe contents or future tenant business data through platform reports; cannot switch into a tenant without an explicit membership |
| Postal-directory deployment operator      | Offline/bootstrap import and activation for an explicitly configured country   | Can stage an authorized source artifact, inspect row-level validation counts, and atomically activate a valid immutable version   | Has no browser mutation API and cannot provision tenants or alter stored tenant address snapshots through the import command                          |
| Tenant Owner / `tenant:owner`             | Active tenants for which the user has an active owner membership               | Can read tenant profile/configuration, checklist, and own tenant probe resources; can update checklist/probe only                 | Cannot create/deactivate tenants, see platform health, see another tenant, or alter bootstrap roles/policies in FND-01                                |
| Authenticated multi-tenant user           | Active memberships explicitly assigned to the identity                         | Can list membership-safe switcher summaries and select one active tenant                                                          | Cannot submit an arbitrary tenant ID without a membership, select an inactive tenant, or preserve old tenant response/cache state after switch        |
| Unauthenticated or expired-session caller | Login, readiness, and invitation acceptance endpoints only                     | May submit credentials or a valid invitation token                                                                                | Receives a non-enumerating denial for protected data; no tenant existence or record-existence leak                                                    |
| PostgreSQL-backed dispatcher              | Rows leased for one active tenant or platform event                            | May update delivery/job state and append audit/alert data                                                                         | Must not lease inactive-tenant rows or deliver a row under a different tenant context                                                                 |

All protected service and repository entry points accept a typed authorization context constructed from the validated server session. Platform-global access uses a separate explicit `PlatformContext`; it is never represented by a missing tenant filter.

## UX flow

### Primary flow: Platform Admin provisions a tenant

1. The Platform Admin signs in at `/login`. A valid session lands on `/platform/tenants`; an invalid credential shows a generic error and creates no session.
2. The tenant list displays name, code, status, owner invitation status, active user count, last activity, and setup progress. It supports server pagination, status filter, code/name search, and empty/retry states.
3. The Admin selects **Create tenant** and completes one labelled form:

   | Field                  | Type and validation                                                                                                                                                                                                                       | Required/default                                                                                                                |
   | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
   | Tenant name            | Trimmed text, 2–120 Unicode characters                                                                                                                                                                                                    | Required                                                                                                                        |
   | Tenant code            | Uppercase `A-Z0-9-`, 2–30; normalized before validation; globally unique and immutable                                                                                                                                                    | Required                                                                                                                        |
   | Legal name             | Trimmed text, 2–160 characters                                                                                                                                                                                                            | Required                                                                                                                        |
   | GSTIN / tax identifier | Trimmed uppercase text, 2–32, letters/digits/hyphen; tenant locale may later add stricter rules                                                                                                                                           | Required                                                                                                                        |
   | Registered address     | Address line 1, optional line 2, country, pincode, and locality selection when a pincode has multiple results. City and state/region are resolved by the server and displayed read-only; they are not separate inputs in the normal flow. | Required except line 2; country defaults to `IN`                                                                                |
   | Timezone               | IANA timezone selector; must resolve in the runtime timezone database                                                                                                                                                                     | Required; configured default                                                                                                    |
   | Locale                 | Supported BCP 47 locale                                                                                                                                                                                                                   | Required; `en-IN` default                                                                                                       |
   | Currency               | ISO 4217 uppercase code                                                                                                                                                                                                                   | Required; `INR` default                                                                                                         |
   | Fiscal-year start      | Month `1..12` and day valid for every year; February 29 is rejected                                                                                                                                                                       | Required; `4/1` default                                                                                                         |
   | Default legal entity   | Name, code (`A-Z0-9-`, 2–30), and optional GSTIN override                                                                                                                                                                                 | Name defaults to legal name; code defaults to tenant code                                                                       |
   | Support contact        | Name, syntactically valid email, optional E.164 mobile                                                                                                                                                                                    | Name/email required                                                                                                             |
   | Owner                  | Name and normalized email                                                                                                                                                                                                                 | Required                                                                                                                        |
   | Branding               | Optional short name (2–32), primary/accent `#RRGGBB`; contrast preview warns/fails if text contrast is below WCAG AA for the chosen foreground                                                                                            | Short name defaults to tenant name; neutral accessible colours default                                                          |
   | Active state           | Checkbox                                                                                                                                                                                                                                  | On by default; creating inactive is permitted and creates a suspended invitation event that is not deliverable until activation |

4. Client validation runs on blur and submit; the backend repeats all validation. Submit sends a generated `Idempotency-Key`, disables duplicate submission, and displays progress without optimistic success.
5. One database transaction creates the tenant, legal entity, canonical legal-entity organization root and scope, configuration defaults, checklist, owner membership placeholder, hashed invitation, one outbox delivery request, platform audit record, and initial report facts. Any failure rolls back all rows and returns a retryable correlation ID.
6. Success opens a detail page showing provisioning state, checklist progress, invitation expiry/delivery state, and—in local development/E2E only—the invitation URL returned once with a **Copy invitation link** action. Refresh never reveals the plaintext token again. Replaying the same idempotency key and identical body returns the original resource and does not create another invite/event; a changed body with the same key returns `409`.

### Pincode-first registered-address flow

1. The form defaults country to India and focuses **Pincode** before any city/state control. For `IN`, it accepts exactly six ASCII digits, uses `inputmode="numeric"` and an autocomplete-compatible postal-code name, and starts lookup only after all six digits are present. Changing country or pincode clears every prior locality selection and derived value immediately.
2. The frontend performs a debounced exact lookup against the PostgreSQL-backed reference endpoint. While lookup is pending, it shows **Finding city and state…**, marks the result region busy, and prevents tenant submission. Requests are cancellable; a response for an older country/pincode is discarded.
3. One matching locality is selected automatically. If several directory rows share the pincode, the user chooses a labelled locality/post-office result from a select/search control; duplicate labels include district so options remain distinguishable. City and state appear as read-only fields/text after selection and are announced through a polite live region. The form posts the selected `postalLocalityId`, country, and pincode, never user-authored city/state.
4. If several locality rows resolve to the same locality/city/state tuple after normalization, the API de-duplicates them. If locality entries disagree on city or state, no value is guessed: explicit locality selection is required.
5. No result shows **Pincode not found** and a retry action. A network/server failure shows a distinct **Could not check pincode** message and retry; it must not be presented as an unknown pincode. Submission remains blocked in both states. Manual unknown-pincode exceptions are deliberately deferred until the shared address policy is designed for the master-data features; FND-01 never accepts free-text city/state.
6. On submit, the backend resolves the selected ID again in the same transaction, verifies it is active and belongs to the posted country/pincode, and derives canonical locality/city/state and directory version. Client-supplied derived fields are rejected as unexpected input. A row retired between lookup and submission returns `409 POSTAL_REFERENCE_CHANGED`; the UI clears derived values, reloads choices, preserves address lines, and asks the user to select again.
7. Tenant detail and downstream address readers render the stored snapshots plus pincode and immutable directory provenance.

### Primary flow: owner accepts invitation and enters the tenant

1. The owner opens `/accept-invitation?token=...`. The frontend exchanges the token for a redacted invitation preview (tenant display name, owner email mask, expiry).
2. The owner supplies display name, password, password confirmation, and accepts the local terms acknowledgement. Password policy is a minimum of 12 characters and checks confirmation; richer policy/MFA belongs to FND-02.
3. The backend hashes the password using the selected approved password-hashing library, marks the invitation accepted exactly once, activates the membership, creates a rotated opaque session, and appends audit events in one transaction. Token replay returns a generic invalid/used response and creates no second user, membership, or session.
4. The owner lands on `/app/setup`. The page renders tenant branding and eight checklist items: organization, users, branches, clients, vendors, commercial settings, imports, and branding. In FND-01, only branding is marked complete by the bootstrap configuration; future-feature items link to an unavailable explanatory state rather than fake implementations.
5. The header shows the active tenant but no switcher when exactly one active membership exists.

### Primary flow: switch active tenant

1. A fixture/user with two active memberships sees a labelled tenant switcher. It lists only active memberships, using tenant name/code/branding without business counts.
2. Selecting Tenant B asks the backend to switch the session to B. The backend verifies active user, active membership, and active tenant, rotates the session identifier, updates `activeTenantId`, and returns a new context version.
3. The frontend cancels in-flight tenant requests, clears tenant query/cache/form/draft/navigation state, remounts under the returned context version, and navigates to `/app/setup`.
4. Branding, settings, checklist counts, probe rows, and recent activity are fetched afresh and contain only Tenant B values. Browser back/forward cannot restore Tenant A protected data; stale responses with the former context version are discarded.

### Tenant lifecycle flow

1. Platform Admin opens a tenant detail page and selects **Deactivate**. A confirmation requires typing the tenant code and entering a 10–500 character reason.
2. The backend changes `ACTIVE → INACTIVE` with optimistic version checking, records actor/reason, revokes active sessions whose active tenant is this tenant, and makes its queued jobs/events ineligible for leasing. Records are retained.
3. Owner login/invitation acceptance/switch to that tenant returns the same generic unavailable result without exposing internal status to unauthenticated callers. Multi-tenant users can still access other active memberships.
4. **Reactivate** requires a reason and changes `INACTIVE → ACTIVE`. Existing memberships and data become usable, but revoked sessions are not resurrected; the user signs in again. A still-valid unaccepted invitation becomes deliverable once and may be accepted; expired invites remain expired.

### Tenant probe isolation flow

The tenant setup page includes a clearly labelled **Isolation test records** development/admin card. Tenant Owners can create, list, search, open, update, and export simple probe records (`label`, `note`). The UI never accepts a tenant ID. Direct API requests for another tenant's UUID return the same `404` envelope as an unknown UUID. The feature also stores one small PostgreSQL document payload and one event/report projection per probe so automated tests exercise every current tenant-owned storage path. The card can be hidden outside local/test environments without removing APIs or tests.

### Validation, loading, empty, error, retry, and stale states

- Forms preserve non-secret values after server validation errors and place an error summary before the form with links to invalid controls. Secret/token/password fields are cleared when appropriate.
- Unique code and normalized owner-email conflicts return `409` with a field-safe message. Database identifiers, SQL detail, token hashes, tenant existence, and cross-tenant record existence never appear.
- List and report pages use visible skeleton/loading labels, meaningful empty states, disabled paging during fetch, and a retry action for network/server failures.
- State-changing actions use an idempotency key and remain safe if the browser retries after an ambiguous timeout.
- Version conflicts return `409 VERSION_CONFLICT` with current safe fields; the UI offers reload and does not silently overwrite.
- A session invalidated by deactivation or expiry clears protected frontend state and returns to login with a generic message.
- A stale tenant-context response is ignored when its response context version does not match the current session context version.
- Readiness degradation is shown on the Platform report without exposing credentials, SQL, stack traces, or cross-tenant content.
- Postal lookup distinguishes incomplete input, loading, one result, multiple results awaiting selection, no result, unavailable/retry, stale selection, and privileged manual exception. A cached browser result is advisory only; tenant creation always revalidates against PostgreSQL.

### Responsive and accessibility behavior

- Primary pages work at 320 CSS-pixel width and desktop widths without horizontal page scrolling; wide tenant/report tables become labelled cards or contained horizontal regions.
- Every control has a programmatic label, errors use `aria-describedby`, the error summary receives focus, dialogs trap/restore focus, and status is not communicated by colour alone.
- All flows support keyboard-only operation with visible focus. Tenant switch announces the new active tenant through a polite live region.
- Colour inputs include text values and previews; AA contrast is enforced for the default content foreground.
- Page titles and landmarks distinguish Platform Admin and tenant areas. Copy-link success is announced without revealing the link to assistive logs after navigation.

## Data model and migration

### Entities and relationships

All IDs are UUIDs generated by PostgreSQL or the application. All mutable records carry `created_at`, `updated_at`, and integer `version`; timestamps are `timestamptz` in UTC. Email and code normalization occurs before persistence.

Every other row representing tenant behavior has a non-null `tenant_id`, except platform-level idempotency/events/jobs/audit/alerts where a `scope`/type check requires `tenant_id IS NULL`. Tenant-owned outbox/job/audit rows require a non-null tenant.

### Invariants, indexes, and tenant isolation

1. All tenant-owned tables declare `tenant_id UUID NOT NULL REFERENCES app.tenants(id) ON DELETE RESTRICT`; no cascade deletion is allowed.
2. Tenant natural-key indexes lead with `tenant_id`. Foreign keys between tenant-owned records include the tenant key (composite unique/foreign-key pattern) so a child cannot reference a parent in another tenant even if an application bug supplies its UUID.
3. PostgreSQL row-level security is enabled and forced on tenant-owned base tables. Policies compare `tenant_id` to a transaction-local context set by the tenant repository unit of work. Platform-only repositories are separate and explicitly reviewed; “no tenant” never grants tenant-row access.
4. A request transaction derives the tenant from `sessions.active_tenant_id` and an active membership/tenant join, then sets the database context. Request body/query/path tenant IDs are ignored for context and rejected where supplied unexpectedly.
5. Repository interfaces require `TenantContext`; raw Prisma access is private to the database package. Escape-hatch unscoped methods have `platform` in their name, require `PlatformContext`, and cannot return tenant business payloads.
6. A migration-policy test queries PostgreSQL catalogues and fails for any table outside an approved control-plane allow-list that lacks a non-null tenant column, forced RLS, a matching policy, and a tenant-leading index. A second reflection test discovers every registered tenant-owned repository/resource and executes A/B negative access.
7. Cross-tenant known UUID and unknown UUID produce the same status, error code, and response shape. Search counts, pagination totals, exports, report projections, document metadata/content, alerts, outbox payloads, and job leases are scoped before aggregation.
8. `tenants.code` is globally unique and immutable. Tenant status transitions allow only `ACTIVE ↔ INACTIVE`; delete is absent.
9. At most one default legal entity exists per tenant (partial unique index), and exactly one is created during provisioning together with the active top-level `LEGAL_ENTITY` organization node, canonical authorization scope, and closure self-row. Existing tenant hierarchies are repaired by the forward migration or rejected with an actionable invariant error when duplicate legal-entity roots are ambiguous.
10. At most one current owner invitation exists for a tenant/normalized email; provisioning creates exactly one invitation and one delivery event. Acceptance is conditional on unaccepted, unrevoked, unexpired invitation and active tenant.
11. Idempotency stores a hash of the key and request. Matching retry returns the original response; mismatched request returns conflict; secrets and plaintext tokens are excluded from replay storage. The local one-time URL is therefore returned only on the initial successful request, not an idempotent replay.
12. Audit rows are append-only. Database permissions/triggers reject update/delete by the application role where feasible and tests verify the repository exposes no mutation.
13. Session, invitation, CSRF, and idempotency keys are compared by cryptographic hash; plaintext values exist only in process memory/secure cookie/one-time response.
14. All JSON configuration is validated against a versioned schema on write and read. Invalid bootstrap templates fail startup/provisioning before partial tenant creation.
15. Postal reference tables are explicitly allow-listed global reference data and therefore do not carry `tenant_id` or tenant RLS. The runtime application role has `SELECT` only; a separate migration/bootstrap privilege performs versioned imports and activation. Tenant-scoped roles cannot mutate directory rows through any API.
16. `postal_code_localities` has an index on `(country_code, postal_code, active)` and foreign keys to an immutable directory version. A partial unique index allows only one `ACTIVE` directory version per country. Activating a new version and retiring the former version is one transaction; historical versions referenced by addresses are retained.
17. Every newly provisioned tenant address records `postal_locality_id`, `postal_directory_version_id`, canonical locality/city/state snapshots, and lookup provenance `DIRECTORY`. Existing addresses are retained as `LEGACY_SNAPSHOT`; FND-01 does not create manual exceptions.
18. Tenant-create validation accepts only country/pincode/postal-locality selection for the normal path. It rejects client-provided city/state and validates the selected row against the exact country/pincode and active directory version inside the provisioning transaction. This reference selection is not a tenant-authorization boundary and does not weaken server-derived tenant context.

### Migration/backfill and reversal plan

- The initial committed Prisma migration creates extensions required for UUID generation, schemas, enum/check constraints, tables, composite keys, indexes, forced RLS policies, audit protections, and reporting views in dependency order.
- Migration verification runs once against a newly provisioned empty `logistics_test` database and once against an already migrated database to prove idempotent deployment. It verifies migration history and required schema/database connectivity.
- Seed commands are explicit and idempotent; normal application startup does not silently seed tenants. E2E reset truncates only this project's test schemas using an allow-listed script and never touches `logistics`, another database, the central container, or volume.
- Because this is the first application migration, no production backfill is required. A forward reversal is a new reviewed migration that disables feature entry points and removes only unreferenced bootstrap objects; deployment scripts never auto-drop schemas/data. The initial migration is not rolled back by deleting the shared database.
- The remediation migrations create the two postal reference tables and enrich tenant registered-address JSON with postal reference, version, and provenance metadata. Existing tenant rows keep their current city/state snapshots and are marked `LEGACY_SNAPSHOT`; they are not silently re-geocoded. A later explicit, audited reconciliation may link them to a directory row.
- Local/E2E bootstrap loads a small deterministic fixture containing single-result, multi-locality, and unknown Indian pincodes. Production bootstrap imports a repository-pinned, authorized India postal-directory artifact through a checksum-verifying, transaction-safe command: normalize into `STAGED`, reject malformed/duplicate/conflicting rows with a report, verify non-zero coverage and expected country, then atomically activate. Re-running the same source checksum is a no-op. A different checksum creates a new immutable version rather than editing active rows.
- Deployment readiness fails with a safe actionable status when `IN` is configured as a supported tenant country but no active Indian directory exists. Runtime never downloads postal data and the shared PostgreSQL container remains the only infrastructure dependency.
- Forward recovery is to activate a corrected directory version. Reversal disables the lookup entry point without dropping referenced directory versions or changing stored address snapshots.

## Domain rules and calculations

### Tenant provisioning state and transaction

- API status is derived from the atomic transaction: there is no partially provisioned tenant visible after a failed transaction.
- Defaults are copied from application configuration at provisioning time with a template/schema version so later code-default changes do not silently mutate existing tenants.
- Default role configuration includes only `TENANT_OWNER` as a bootstrap role. The richer baseline role catalogue is introduced and migrated by FND-02.
- Default reason lists include tenant lifecycle and setup categories; default threshold configuration uses product defaults but remains tenant data. No customer name/code/value is embedded.
- Setup progress is `COMPLETE items / total applicable items × 100`, represented as integer numerator/denominator plus display percentage rounded to the nearest whole percent. `NOT_AVAILABLE` remains applicable until its feature exists and is not counted complete.

### Invitation and session states

- Invitation states are derived in order: `ACCEPTED`, `REVOKED`, `EXPIRED` (`now >= expires_at`), `DELIVERY_FAILED`, `PENDING_DELIVERY`, `DELIVERED`. Equality at expiry is expired.
- Delivery uses an outbox deduplication key based on invitation ID and event version. The dispatcher leases with PostgreSQL `FOR UPDATE SKIP LOCKED`, records attempts, and never processes tenant work while tenant is inactive. Repeated processing cannot create a second logical delivery.
- Acceptance and user creation are transactional and concurrency-safe. Two concurrent acceptance attempts yield one success and one generic invalid/used result.
- Sessions have an idle and absolute UTC expiry configured by environment. Each authenticated request checks active user; tenant routes additionally check active tenant and membership. Switching rotates the cookie token and increments context version.
- A user with zero active memberships has no active tenant and cannot access tenant routes. One active membership is selected automatically. Multiple memberships require the most recently valid selection or an explicit selection.

### Tenant lifecycle and jobs

- Deactivation uses optimistic concurrency and records a mandatory reason. It revokes sessions currently active in the tenant and prevents new tenant sessions, invitation acceptance, tenant repository operations, outbox leasing, and job leasing.
- Rows already leased when deactivation commits must re-check tenant status immediately before side effect/acknowledgement; if inactive, they release/defer without delivery. There is no deletion.
- Reactivation does not reset configuration, memberships, versions, audit, or data. It does not unexpire invitations or un-revoke sessions.

### Time, concurrency, and historical behavior

- Persist instants as UTC `timestamptz`; return RFC 3339 UTC strings. Render calendar/date labels in the tenant IANA timezone. The Platform report uses the Platform Admin's configured timezone or UTC when absent.
- Fiscal-year month/day is a business calendar value, not converted to an instant. February 29 is excluded so every year has a start date.
- Every mutable update includes expected `version`; success increments by one. Stale writes fail with no partial mutation.
- Historical audit/config snapshots remain unchanged when current tenant profile or default templates change.

### Postal resolution and address history

- For country `IN`, normalize pincode by trimming outer whitespace and then require exactly `[0-9]{6}`; do not strip internal spaces or coerce non-ASCII digits. Postal codes remain strings so leading zeroes are preserved for countries that allow them.
- Lookup is an exact match against the active directory version. Search is bounded to 100 normalized locality choices and sorted by locality, city, district, then stable ID. The response includes a stable row ID and display fields but not source-file internals.
- The selected reference row is authoritative only at creation time. The address stores canonical locality/city/state text and directory version so a later spelling correction or postal-boundary change never rewrites historical tenant identity, audit, documents, or reports.
- Manual exception is allowed only when the exact lookup completed successfully with zero rows and only to `platform:admin`. Reason and manual locality/city/state values are snapshots. Later directory refresh does not auto-convert the exception; an explicit reviewed reconciliation is required.
- Pincode lookup is a read and needs no idempotency key. Directory imports and version activation are idempotent by source checksum and serialized per country with a PostgreSQL advisory or row lock.
- This resolver and response DTO are the reusable address contract for MST-01 organization/geography, MST-02 client locations, and MST-03 vendor/driver addresses. Those features own adopting the component, their actor permissions, and any context-specific geofence behavior; FND-01 does not change their production forms in this slice.

## Reports and alerts

### Platform health report

The Platform Admin report contains no tenant probe labels/notes, documents, event payloads, or future business aggregates. It shows:

- tenant counts: total, active, inactive;
- per tenant: code/name/status, active accepted membership count, pending/expired owner invitation state, setup complete/applicable counts and derived percentage, last tenant activity UTC/display time, pending/failed outbox count, pending/failed job count, last projection refresh;
- project PostgreSQL database size from `pg_database_size(current_database())`, labelled as shared-container project database usage, not tenant business storage;
- backend readiness and migration state;
- integration health as `Not configured` in FND-01 rather than a false success;
- latest safe failure class/time/correlation ID for jobs/events, never raw payload/error/SQL;
- active postal-directory country/version/source date/import time, active row/postal-code counts, and manual address-exception count; source freshness is informational unless an operator-configured maximum age is exceeded;
- freshness timestamp from the reporting view/projection.

Every displayed count drills down to a permission-safe filtered detail list or is clearly marked non-drillable. SQL reconciliation tests compare per-tenant report counts to canonical tenant-scoped base rows. Aggregate totals equal the sum of visible per-tenant rows for the selected filter; project database bytes are not allocated or summed by tenant.

## Audit, observability, and security

- Append audit events for login success/failure class (never password), logout, invitation preview/acceptance outcome, tenant provision/lifecycle change, tenant switch, checklist change, probe mutation/export/document access denial, platform report access, alert resolution, job/delivery state transition, authorization denial, postal-directory version import/activation/failure, and every manual postal exception/reconciliation.
- Audit before/after JSON is field-allow-listed. Passwords, tokens, token hashes, session/CSRF values, document bytes, and raw PostgreSQL errors are prohibited. Tax/support data is included only when necessary and masked in non-detail events.
- Structured logs include timestamp, level, service, correlation ID, safe actor ID, effective tenant ID, route/event type, outcome, duration, and error class. They exclude request bodies for auth/provisioning and never log secrets.
- Passwords use a memory-hard approved hash with per-password salt and bounded verification parameters. Opaque session/invitation/CSRF tokens use cryptographically secure randomness and one-way hashing at rest.
- Cookies are `HttpOnly`, `SameSite=Lax` or stricter, path-limited where practical, and `Secure` outside explicit local HTTP mode. State changes validate Origin and CSRF token. CORS permits only configured frontend origins with credentials.
- Apply CSP, frame-ancestors, referrer, MIME-sniffing, and permissions headers at frontend/backend boundaries. Escape all rendered configuration and CSV formula-leading content.
- Login and invitation acceptance have bounded PostgreSQL-backed attempt counters and generic errors. FND-02 can expand adaptive policies; no in-memory-only limiter is relied on for security.
- Error responses never reveal tenant existence, membership, other-tenant record existence, schema/table names, SQL, stack traces, credential state, or token validity beyond the minimum invitation UI state.
- `/health/ready` verifies database connection and migration state; tenant invariant checks expose only pass/fail. Platform alerts preserve actionable safe evidence.
- Postal lookup logs include correlation ID, normalized route, country, outcome class (`FOUND`, `NOT_FOUND`, `INVALID`, `UNAVAILABLE`, `STALE_SELECTION`) and duration, but not full address lines or actor-entered exception text. - Metrics also include request count/latency/status by normalized route, authorization denials, active sessions, provisioning outcomes, outbox/job states, tenant-switch outcomes, and projection freshness. Tenant IDs are bounded labels only in local/debug output; customer names, emails, tax IDs, and tokens are never metric labels.
- Secrets come only from validated environment configuration. Startup rejects missing/placeholder secrets outside local/test. `.env`, logs, traces, screenshots, and generated reports remain uncommitted.

## Platform tenant-user administration extension

This extension closes the operational gap between the Platform Admin tenant registry and the tenant-scoped FND-02 access directory. It is a Platform Admin support and governance surface, not tenant impersonation. The selected tenant ID scopes every query and mutation, and the platform actor remains the recorded actor throughout.

### Actors, authorization, and scope

| Actor                                           | Allowed                                                                                                                                                            | Explicitly denied                                                                                                                                                                                                           |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Platform Admin with an active platform session  | List and inspect memberships for the selected tenant; view safe onboarding evidence; edit tenant-specific membership profile fields; suspend/reactivate membership | Create or assume a tenant session; read/set a password; edit an invitation or accepted global identity destination; bypass role/audience compatibility, MFA policy, or final-owner safeguards; read tenant business records |

| Other tenant users and anonymous users          | None                                                                                                                                                               | Discover tenant, membership, activation, onboarding, role, session, or MFA existence through platform routes                                                                                                                |

Authorization is enforced in the platform service before any query. Every membership lookup is conjunctive on `tenant_id = :tenantId AND id = :membershipId`; a membership from another tenant is indistinguishable from an unknown ID. The route tenant ID is only an explicit Platform Admin selection, never a tenant-context override for ordinary sessions. Platform actions reuse the canonical FND-02 validation and lifecycle policy functions rather than directly updating tables through a weaker path.

### UX flow and states

1. `Platform Admin → Tenants → <tenant> → Users` shows a searchable, server-paginated table with display name, masked email/mobile, employee code, audience, membership state, activation state, role labels, onboarding percentage/state, last successful login, MFA state, and active-session count.
2. The initial UI supports bounded search and membership-state filtering. The API also accepts activation state, audience, and role filters. Complete server paging/sort and onboarding-state filtering remain a recorded follow-up; all current counts are computed after the tenant predicate.
3. Selecting a row opens a labelled dossier, not raw JSON. It contains Profile, Activation, Access, Onboarding, Security/sessions, and Activity panels. Every derived onboarding stage shows its source, state, explanation, and the CTA that can resolve it.
4. Profile editing supports tenant-specific display name, employee code, and portal audience. Invitation and accepted global identity destinations are read-only because changing either safely requires atomic token rotation/global-identity recovery.
5. Role/scope editing remains in the tenant-authorized FND-02 directory. A separate planned Platform workflow will reuse its evaluator rather than accepting identifiers from free text.
6. `Disable` maps to membership `SUSPENDED`; `Enable` maps to `ACTIVE`. The confirmation shows session impact, requires a reason, protects the final active Tenant Owner, and never deletes membership/history. Suspension revokes that membership's active sessions immediately. Reactivation does not restore revoked sessions, expired invitations, disabled MFA factors, or removed assignments.
7. Arbitrary membership invitation reissue/revoke plus session/MFA reset are planned Platform follow-ups. The existing tenant-owner activation replacement and tenant-authorized FND-02 workflows remain available. Passwords are never displayed or assigned.
8. The tenant header also retains the tenant-level setup summary and links to the canonical setup pages. Platform Admin may update only the tenant-specific user profile and lifecycle sources described here. Derived onboarding percentages and tenant setup states cannot be typed or forced complete; they change only when their canonical source data satisfies the rules.

Loading uses skeleton/table placeholders without stale actions. Empty states distinguish “no users” from “no filter matches” and retain the tenant summary. Mutations disable only the affected action, preserve safe form input on validation/version errors, and reload the row/dossier after success. A `409 VERSION_CONFLICT` shows that the record changed and requires a fresh preview; it never silently overwrites. Unknown/foreign membership IDs return the same non-leaking `404`. Service errors show correlation ID and retry without exposing SQL, tokens, or foreign metadata.

On narrow screens, the directory becomes labelled summary cards and dossier panels stack; the primary lifecycle action remains reachable without horizontal scrolling. Status is conveyed by text and icon as well as colour. Tabs, dialogs, menus, search, filters, forms, progress indicators, and confirmation messages are keyboard and screen-reader operable; focus moves to the error summary or success status after a mutation.

### Onboarding calculation and data contract

Onboarding is a read-time projection from canonical data, not a user-editable flag and not a new source of truth. It returns `asOf`, `state`, `completedStages`, `applicableStages`, integer `percent`, and ordered stages containing `code`, `label`, `state`, `explanation`, `source`, and optional permitted CTA.

| Stage             | Applicable/completion rule                                                                                                                                                                                                |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PROFILE`         | Applicable to every membership; complete when non-blank display name, unique employee code, valid audience, and at least one invitation/contact destination are present                                                   |
| `ACTIVATION`      | Applicable to every membership; complete when membership has an accepted user identity and active credential state; pending/expired/revoked invitation reports its exact safe state                                       |
| `ACCESS`          | Applicable to every membership; complete when at least one currently effective role assignment has a currently effective valid scope grant and passes audience compatibility; the protected owner floor still applies     |
| `PERSONA_LINKAGE` | Applicable to external `CLIENT`, `VENDOR`, or `DRIVER` audiences and to internal users where tenant policy requires employee linkage; complete only when the canonical linked record belongs to this tenant and is active |
| `MFA_POLICY`      | Applicable only when effective tenant/role policy requires MFA; complete when a verified, non-disabled factor satisfies that policy; otherwise returned as `NOT_APPLICABLE` and excluded from the denominator             |

`percent = floor(completedStages * 100 / applicableStages)` using integers. Zero applicable stages is invalid because `PROFILE`, `ACTIVATION`, and `ACCESS` always apply. Overall state is `COMPLETE` only at 100%; `BLOCKED` when any applicable stage has an expired/revoked invitation, inactive required linkage, incompatible role/audience, or unsatisfied mandatory MFA; `NOT_STARTED` when zero applicable stages are complete and none is blocked; otherwise `IN_PROGRESS`. The response identifies stale projection timestamps, but the mutation path re-reads canonical rows in one transaction and never authorizes from a cached percentage.

No new persisted onboarding table is required. Existing `tenant_memberships`, `users`, invitations, role assignments/grants, MFA factors, sessions, and audience-specific canonical link records remain authoritative. Add only tenant-leading indexes or a reporting projection if measurement demonstrates the bounded live query cannot meet the existing directory latency objective. Any projection must carry `asOf`, be idempotently rebuilt from canonical records, and never drive authorization.

The delivered core returns `percent`, overall `status`, named checks, and safe explanations from live canonical reads. Adding `asOf`, ordered stage/source metadata, internal employee-link policy, and canonical CLIENT/VENDOR membership links is planned in `TODO.md`; until then a missing external linkage is reported `BLOCKED`, never complete.

### Platform tenant-administration completion contract

This contract supersedes the narrower follow-up statements above for four explicitly requested Platform Admin operations. It does not permit tenant impersonation, password disclosure, direct database editing, or forcing derived setup/onboarding state.

#### UX and explicit behavior

1. The user dossier shows the tenant membership's invitation/login destination masked by default. A clearly labelled **Reveal email** or **Reveal mobile** action (according to destination type) opens a confirmation that explains the sensitive read and requires a reason of 10–500 characters plus the acting Platform Admin's current password. On success only that selected tenant membership destination is shown in the dossier for at most 60 seconds with explicit **Copy destination** and **Hide now** controls. It is cleared on close, navigation, tab background timeout, session/context change, or error. The operation never discovers or returns a different global-identity destination from another membership. List/search/export/browser storage never receives the full value.
2. **Edit user details** is a visible primary dossier action rather than an always-open ambiguous form. It opens labelled fields for tenant-specific display name, employee code and portal audience, shows the masked immutable login destination, explains why email is managed separately, requires reason/current version, and offers Save/Cancel. Successful save refreshes profile, permitted actions and derived onboarding; validation/conflict preserves the form.
3. For an eligible activated single-tenant identity, **Generate password-reset link** is visible only when permitted. Confirmation requires the acting Platform Admin's current password and a reason, clearly states that generation does not itself change the user's password, and does not offer an override path. The server refuses the action when the target identity has more than one active tenant membership or is the acting Platform Admin's own identity; those users must use the normal self-service/provider recovery flow. The successful response shows the reset URL once with explicit **Copy reset link** and **Hide now** controls, clears it within five minutes or on navigation/session change, and never makes it retrievable from detail, replay, audit, logs or export. Pending invitations continue to use activation-link replacement instead.
4. Tenant detail adds an **Onboarding & masters** section sourced from canonical setup and master tables, not static checklist labels. It shows each applicable stage with `state`, canonical record count, blocking reason, `asOf`, and actual representative safe records (name/code/state plus stage-relevant summary) from Organization/legal entities, Users/access, Branches/locations/employees, Clients/client locations/contracts/lanes, Vendors/vehicles/drivers/compliance, Commercial settings/rates/SLAs, Imports and Branding. A stage is Complete only from its canonical completion rule; unavailable modules are explicitly `NOT_AVAILABLE`, not “complete”. Representative rows are bounded and provide **View all** when a Platform-context list exists.
5. Each stage exposes explicit **Add**, row-level **Edit**, and section-level **Manage** actions only where a selected-tenant Platform-context typed route and owning canonical service are implemented. These routes retain the Platform session/actor, accept an explicit selected tenant context, and never manufacture a tenant session, redirect to a tenant-context URL, or write generic JSON. Every selector/query/mutation remains conjunctive on the selected tenant, respects natural-key/version/deactivation rules, and records `impersonation=false`. Where no Platform-context editor exists, the page shows the actual records read-only and an honest “Management is not available from Platform administration” explanation; it renders no dead or tenant-context link.
6. Loading uses stable skeletons; sensitive actions remain unavailable while permissions/current version are unknown. Empty data distinguishes “no canonical records” from “not available” and offers the appropriate Add/Manage CTA. A stale version or changed identity impact requires a fresh confirmation. Errors include a correlation ID and retry without leaving a revealed email/reset URL visible.

#### Authorization, data, API, and audit invariants

- All four operations require a current Platform Admin session and explicit protected actions returned in `permittedActions`: `REVEAL_DESTINATION`, `EDIT_PROFILE`, `GENERATE_PASSWORD_RESET`, and per-stage `VIEW_MASTER`/`MANAGE_MASTER`. The server rechecks authorization and selected-tenant membership on every call; UI visibility is not authorization.
- Destination reveal is a sensitive read, not a profile mutation. The server verifies the supplied current password against the acting Platform Admin's credential using the normal constant-time password path, applies the protected-action rate limit, and never persists/returns/logs that password. It returns only `{type, destination, revealedUntil}` for the destination stored on the selected tenant membership with `Cache-Control: no-store`; the response is excluded from service-worker/browser caches, idempotency storage and telemetry. Audit records actor, tenant, membership ID, reason, destination type, outcome, correlation ID and `impersonation=false`, but only a masked destination and never its full value.
- Password reset reuses the FND-02 reset-token model: a cryptographically random bearer is stored only as a hash, scoped to the global user, expiring and single-use. The URL places the bearer in a fragment and the reset page submits it only to the fixed completion endpoint. Generation invalidates older live reset tokens for that identity; successful completion changes the Argon2 password and revokes all sessions/outstanding reset tokens across memberships. Generation alone does not revoke sessions or change credentials.
- Platform-generated reset is allowed only for an active local-password identity with exactly one active tenant membership, and that membership must be the selected membership under the selected tenant. The server verifies the acting Platform Admin's supplied current password and protected-action rate limit before token rotation. Reset is denied, without an override/impact-confirmation path, for a shared multi-tenant identity, invited/unaccepted user, suspended global identity, external-only authentication, the acting Platform Admin's own identity, or an identity whose policy requires another recovery workflow.
- Master/setup summaries are read-time canonical projections. No client may submit stage state, count, percentage or completion. Master updates invoke the owning feature service with a `PlatformSupportContext { actorId, selectedTenantId, reason, correlationId }`; business validation, tenant foreign keys, optimistic version, idempotency, audit/outbox and effective-date/history rules are unchanged.
- No new plaintext-sensitive column is introduced. Add only forward-safe indexes or a reporting projection carrying `tenant_id` and `asOf` if canonical bounded queries need it; projections never authorize or drive completion without canonical revalidation.

#### Acceptance criteria

- **FND01-PTA-AC01:** Directory/detail/export remains masked by default; only a confirmed, reasoned `/reveal-destination` call with the acting Platform Admin's valid current password returns the selected tenant membership destination, and every success/denial is audited without storing the full destination.
- **FND01-PTA-AC02:** Revealed email disappears on timeout/hide/navigation/session change and is absent from cache, browser persistence, replay responses, logs, errors, metrics and exports.
- **FND01-PTA-AC03:** Edit user details is clearly visible and versioned; it edits only permitted tenant-profile fields, explains immutable login identity, recomputes onboarding and never overwrites a concurrent change.
- **FND01-PTA-AC04:** After current-password step-up, Platform Admin can generate/copy/hide a one-time password-reset link only for an eligible active single-tenant identity; self-reset and shared multi-tenant identities are refused without override, replay cannot reveal the link, completion revokes sessions/tokens, and no password is displayed or assigned.
- **FND01-PTA-AC05:** Tenant detail shows actual canonical onboarding/master stages, counts, blockers and bounded representative records for the selected tenant; displayed status reconciles to independent canonical queries at `asOf` and cannot be forced by the client.
- **FND01-PTA-AC06:** Every displayed Add/Edit/Manage action uses an implemented Platform-context typed route and owning master service with selected-tenant authorization, validation, versioning, idempotency and audit; otherwise records remain read-only with an honest explanation and no dead/tenant-context link.
- **FND01-PTA-AC07:** Non-platform and cross-tenant direct-ID calls are non-leaking; protected actions are denied server-side even if manually invoked, and Platform Admin never acquires a tenant session.
- **FND01-PTA-AC08:** Desktop/mobile and keyboard flows cover confirmations, copy/hide, detail editing, stage drill, loading/empty/error/retry and stale-impact recovery without exposing sensitive values.

Safe configurable assumptions: destination reveal lasts 60 seconds; reset-link display lasts five minutes; reset-token expiry follows the existing FND-02 policy. Both sensitive actions require the current password on every attempt rather than relying only on session age. These values may be tightened by security configuration without changing the contract.
