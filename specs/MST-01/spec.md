# MST-01 — Organization, employee, and geography masters

**Status:** Verified
**Feature source:** `FEATURES.md` section `MST-01 — Organization, employee, and geography masters`
**Owner:** Primary agent

## Problem and outcome

The canonical backend has tenant-scoped organization nodes, hierarchy closure, employees, operational assignments, scope-aware reads/writes, cycle prevention, impact counts, deactivation guards, audit events, and state reports. The current product surface does not make those capabilities understandable or complete: Masters opens directly on a generic organization form; there is no landing hub or persistent master navigation; record details expose database-shaped values; organization addresses accept free text and comma-separated PIN codes without deriving locality/city/state; employee designation, region coverage and linked roles are absent; create-only generic forms do not provide coherent edit, impact, or reassignment journeys; and ownership reports/alerts are not presented as an operator workflow.

MST-01 remediation will make organization and people administration discoverable and operable. A tenant administrator can navigate a hierarchy, create and edit legal entities/regions/branches/teams/hubs, capture canonical PIN-derived geography and a structured geofence, maintain structured employee profiles and linked access, preview and resolve deactivation impact, and verify that hierarchy-driven scope changes propagate to lists, exports, alerts, and audit evidence.

| Employees      | Tenant-scoped employee rows, manager/home-node/member references, effective-dated operational assignments                          | Designation and region coverage, structured table/detail/edit, role/access summary, searchable selectors, manager-cycle validation, clear optional-field help           |

## In scope

- A `/app/masters` landing hub, persistent Masters subnavigation, and grouped links to Organization & geography, Employees & ownership, Clients, Client locations, Contracts & lanes, Vendors, Fleet, and Drivers. MST-01 owns the hub and its Organization & people experiences; links to MST-02/MST-03 surfaces may expose existing routes without changing those feature contracts.
- A hierarchy tree and permission-scoped table for legal entities, regions, branches, teams, and hubs, with search, state/type filters, selection, create, view, edit, move, enable, disable, pagination/export entry points, and explicit empty/loading/error/retry states.
- Valid hierarchy rules: `LEGAL_ENTITY` is a root; `REGION` belongs to a legal entity; `BRANCH` belongs to a region; `TEAM` belongs to a branch or hub; `HUB` belongs to a region or branch. Existing valid rows outside these rules remain readable as legacy exceptions until an administrator edits or moves them.
- Structured organization fields: code, name, node type, searchable parent, inherited/overridden authorization scope with help, timezone (default `Asia/Kolkata`), active-from date, optional active-to date, and a structured physical address/geofence where applicable.
- PIN-first Indian organization addresses: address line 1, optional address line 2, country fixed/defaulted to `IN`, six-digit PIN, locality choice when ambiguous, and read-only district/city/state derived from the active PostgreSQL postal directory. City/state are never separately typed.
- A structured geofence editor supporting polygon, fixed point plus radius, and contextual radius. It provides a map interaction and accessible latitude/longitude inputs; users never enter JSON.
- Structured employee list/detail/create/edit forms with employee code, display name, designation, optional email/mobile, searchable manager, searchable home branch/node, zero or more searchable regions, active-from, optional active-to, optional linked user membership, and linked role/access summary.
- Employee operational assignment UI for KAM-to-client, manager-to-organization, traffic-to-organization and queue-owner assignments, with searchable references and date/time controls. The UI constructs request objects; users never enter IDs or JSON directly.
- Deactivation impact preview and atomic reassignment/deactivation for employees and organization nodes; an explicit privileged exception path is allowed only when no safe replacement exists and records the reason, expiry/review owner, affected references, and a visible alert.
- FND-02 integration so organization hierarchy and employee reassignment update effective access for linked memberships and all permission-scoped consumers.
- Organization tree, ownership coverage and exception reports; orphan/inactive-owner alerts; immutable audit history and correlation IDs.
- Forward-safe migrations and compatibility for existing records.

## Out of scope

- Client/location commercial rules (MST-02), vendor/vehicle/driver/compliance behavior (MST-03), and truck/body/cargo reference catalogs (CFG-01/MST-03), other than discoverable links in the Masters hub.
- A general map/GIS server, route optimization, reverse geocoding, live GPS, or adding a new infrastructure service. The baseline remains Next.js, NestJS and PostgreSQL.
- Free-text city/state or an unaudited unknown-PIN override. Unknown PIN exception policy remains a product decision; until approved, unknown PINs block save with retry guidance.
- Creating an application membership or issuing activation links from the employee form. The form links an existing tenant membership and directs authorized admins to FND-02 for invitation lifecycle actions.
- Replacing FND-02 role definitions. MST-01 displays and, for actors with the required identity capability, invokes the existing role/scope assignment service rather than duplicating access logic.
- Bulk file import changes. If a later MST-01 import is added, it must include a downloadable real CSV/XLSX sample and use the same PIN/reference validations.
- Production email/SMS delivery or external map-provider credentials.

## Actors, permissions, and scopes

| ------------------------------------------------------------------ | -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Tenant Owner / `masters.admin`                                     | Entire tenant or explicit delegated organization subtree             | Create/edit/move nodes; create/edit employees; assignments; ordinary reassignment/deactivation  | Cannot access another tenant, assign references outside effective scope, grant roles without identity capability, or bypass impact checks |
| Scoped Master Admin / `masters.admin`                              | Only organization nodes/resources authorized by active FND-02 grants | Same operations within granted subtree; replacement must also be in allowed scope               | Cannot infer hidden IDs: guessed cross-scope/cross-tenant resources return non-leaking 404/403 per established policy                     |

Tenant context is always derived from the authenticated session. Every selector, mutation, report, export, impact calculation and alert drill-down applies both tenant isolation and resource-scope authorization on the server.

## UX flow

### Primary flow

1. Selecting **Masters** opens `/app/masters`, not a creation form. Summary cards show Organization & geography, Employees & ownership, Clients, Contracts & lanes, Vendors, Fleet and Drivers, with counts the actor may see and direct primary actions permitted by capability.
2. A persistent `aria-label="Masters"` subnavigation remains visible on all master routes. The current item is announced, keyboard focus is preserved, and unavailable actions are omitted or disabled with an explanation.
3. **Organization & geography** opens a split hierarchy/table experience. The actor searches or filters by type/state, selects a node, and sees named fields rather than raw object/JSON output. Breadcrumbs show ancestors; children and impact counts are separate tabs/panels.
4. **Create node** asks for node type first, then restricts the searchable parent selector to valid types and permitted active nodes. Timezone defaults to `Asia/Kolkata`; active-from defaults to the tenant-local current date; optional fields are labelled “Optional.”
5. For a physical address, the actor enters address lines and PIN. Six valid digits trigger the authenticated postal lookup. One locality auto-selects; multiple localities require a labelled selection including locality and district. District, city and state appear read-only with a live announcement. Save sends only `postalLocalityId` plus user-entered address lines, never user-entered city/state.
6. The actor chooses geofence mode: draw at least three polygon vertices; select one centre plus radius; or use a radius around the node’s contextual office point. The form presents the structured values and map, while the application generates JSON internally.
7. Save creates the organization node, canonical address snapshot, hierarchy closure and its linked authorization scope atomically. The new node becomes visible in the tree without losing filters. Edit requires the current version; conflicts preserve user input and offer reload/reapply.
8. **Employees & ownership** shows a server-filtered table with employee, designation, manager, home branch, regions, linked-user state, effective roles, active dates and state. Create/edit uses structured fields and searchable selectors only. Email/mobile are validated; mobile accepts readable spacing but persists normalized E.164.
9. Linking a membership shows its activation state and effective roles/scopes. An identity-authorized actor may open the existing role/scope editor; otherwise the section is read-only and explains where access is managed. Selecting regions creates effective-dated coverage assignments; home-node and region choices must be compatible.
10. From an employee detail, the actor adds effective-dated operational assignments using searchable employee/node/client references and native date/time controls. The UI describes each assignment type and whether organization or client is required.
11. **Deactivate** first loads a fresh impact preview. For an employee it lists direct reports, linked membership/access, active assignments, owned clients/locations/open workflows and escalation routes. For an organization node it lists descendants, employees, assignments, client locations, scoped grants, open records and alert routes.
12. If impact exists, the actor supplies permitted replacement employee/node choices and a reason. The server revalidates impact and versions in one transaction, transfers/ends responsibilities, synchronizes affected effective scope, deactivates the record and writes audit/events. If a permitted replacement is impossible, only a `masters.exception` actor may record a time-bound exception; unresolved items remain visible and alerting.
13. Reports show hierarchy/ownership totals with drill-down to the exact filtered records. The Activity & audit link opens a pre-filtered audit search for the selected record/correlation ID.

### Validation, loading, empty, error, retry, and stale states

- Forms show server field errors adjacent to the named field and move focus to the first invalid input. Codes are trimmed/uppercased and tenant-unique. Dates use calendar controls; date-times use date/time controls and are converted using the tenant timezone to UTC instants.
- Parent choices enforce node-type rules. Self-parenting, descendant-parenting, manager self-reference, direct/indirect manager cycles, inactive references and cross-scope references are rejected server-side even if submitted outside the UI.
- PIN must be exactly six digits and start 1–9. Malformed input does not call the API. Unknown PIN, lookup failure and stale directory selection show different messages with Retry; user-entered address lines are retained. City/state never become editable fallback fields.
- Geofence validation: `POLYGON` requires at least three distinct vertices and a closed non-self-intersecting polygon; `POINT_RADIUS` requires exactly one valid WGS84 point; `DYNAMIC_RADIUS` stores no fixed vertices and requires an allowed context (`OFFICE` here); radius is greater than 0 and at most 500 km. Latitude is −90..90 and longitude −180..180. Map clear/undo is available.
- Employee active-to is optional and cannot precede active-from. Manager and replacement must be another active employee. Selected regions must be active regions that contain or are compatible with the home node. Linked membership must belong to the tenant and may link to at most one active employee.
- Lists and selectors distinguish initial loading, incremental search, no records, no matches, permission-limited empty state, server error and retry. Search is debounced and aborts stale requests. Selectors display human labels/codes, never bare UUIDs.
- Impact preview has its own loading/error/retry state and includes `calculatedAt` plus affected record versions. Confirmation with changed impact returns `409 IMPACT_CHANGED`; stale edit/move returns `409 VERSION_CONFLICT`; stale postal selection returns `409 POSTAL_REFERENCE_CHANGED`. Recovery reloads current values/impact without silently discarding entered reason or replacement choices.
- Idempotency replay returns the original response. Reuse of a key with a different body returns `409 IDEMPOTENCY_CONFLICT`. Partial reassignment is rolled back on any failure.
- Empty hierarchy shows a guided **Create legal entity** CTA. Empty employees shows **Add employee** after a branch exists, otherwise a dependency CTA to create organization structure.

### Responsive and accessibility behavior

- At desktop widths the tree and detail/table may share the page; at narrow widths they stack and the selected-node breadcrumb remains available. Tables provide a card/list alternative or horizontal scrolling without clipping actions.
- All controls have programmatic labels, required/optional indication in text, instructions associated with `aria-describedby`, visible focus, and keyboard operation. Status is never conveyed by colour alone.
- Tree navigation uses appropriate tree/treeitem semantics, arrow-key navigation, expanded state, current selection and an equivalent flat table for screen-reader/keyboard users.
- Postal lookup, save, scope refresh and reassignment outcomes use concise polite live regions; destructive confirmation and validation errors use assertive announcements where appropriate.
- The geofence map is not the only input mechanism. Latitude/longitude/radius fields and a vertex table support keyboard and assistive technology; vertex order, add/remove/undo and validation are announced.
- Dialogs trap focus, close with Escape when safe, restore focus to their invoking control, and do not dismiss during a pending mutation.

## Data model and migration

### Entities and relationships

- `app.organization_nodes` remains the aggregate root. Add `address_line1`, `address_line2`, `country`, `postal_code`, `postal_locality_id`, `postal_locality`, `district`, `city`, `region`, `postal_directory_version`, `postal_source`, and `address_verification_state` (`DIRECTORY`, `LEGACY_UNVERIFIED`, `NOT_APPLICABLE`). Keep `latitude`, `longitude` and `geofence`, but validate them against a typed domain schema. `postal_locality_id` references the immutable/versioned postal directory row according to the FND-01 ownership boundary; snapshot columns preserve historical display after directory activation changes.
- `app.organization_closure` remains the transitive hierarchy index. Each node has exactly one depth-0 self row; descendants have one row per ancestor. Node creation/move/deactivation maintains closure and authorization scope linkage in the same transaction.
- Each organization node has exactly one canonical `app.authorization_scope_nodes` row identified by `canonical_resource_id=organization_node.id`, with mapped type `LEGAL_ENTITY`, `REGION` or `BRANCH`; `TEAM`/`HUB` inherit their nearest mapped ancestor unless a dedicated compatible scope type is added by an approved migration. The organization node stores this resolved scope ID.
- `app.employees` adds `designation`. `linked_membership_id` receives a partial tenant-unique constraint where non-null so one active membership cannot represent multiple employees. Existing manager/home-node/version/effective dates remain.
- Add `app.employee_region_assignments`: tenant ID, employee ID, region organization-node ID, effective-from/effective-to, state, created-by/at, version. It is tenant-unique for overlapping active employee/region coverage and only references active `REGION` nodes.
- `app.operational_assignments` remains effective-dated. Add/update indexes for active assignments by employee, organization node and client. All target references are tenant-composite foreign keys.
- Add `app.master_deactivation_exceptions`: tenant, target type/id, impact snapshot, reason, review-owner membership, review-by date, state (`OPEN`, `RESOLVED`, `EXPIRED`), resolution metadata, actor, timestamps and version. Rows are append-audited and never hard-deleted.
- Audit events remain in `audit.audit_events`; domain events/outbox and alerts use existing PostgreSQL facilities.

### Invariants, indexes, and tenant isolation

- Every new application row has non-null `tenant_id`, composite tenant foreign keys, enabled/forced RLS and policies consistent with existing application tables. Postal-reference reads use the restricted directory role; application runtime cannot mutate reference data.
- Codes are uppercase and unique per tenant. Organization type/parent validity is enforced in the domain service and with a defensive database trigger/check where practical. Both organization closure and employee manager graphs reject cycles; maximum supported depth is 12.
- A physical node cannot be created/edited without an active canonical postal selection and complete snapshot. Request city/state/district/locality values are rejected as unknown fields; the server re-resolves `postalLocalityId` and PIN inside the write transaction.
- Geofence is one discriminated shape only: `{mode:'POLYGON', points:[...]}`, `{mode:'POINT_RADIUS', point, radiusKm}`, or `{mode:'DYNAMIC_RADIUS', context:'OFFICE', radiusKm}`. Numeric persistence uses PostgreSQL numeric and domain-safe conversion, not binary floating-point calculations for boundary comparisons.
- Effective ranges are half-open `[effective_from, effective_to)` for date-times. Business dates use tenant timezone; stored instants are UTC. Concurrent edit, move, scope sync, exception resolution and deactivation use record versions/row locks.
- An inactive employee cannot remain manager/active assignee/owner without either completed reassignment or an open privileged exception. An inactive node cannot retain active descendants/resources or active grants without completed reassignment or an open exception.
- All list/report/export/detail queries use `domain_resource_authorized` (or the shared equivalent) and cannot rely on UI filtering.

### Migration/backfill and reversal plan

1. Add nullable columns/tables/indexes/RLS/policies without rewriting existing rows; deploy read-compatible code.
2. Backfill `designation` as null. Backfill canonical scope links where an unambiguous organization/scope mapping exists; record reconciliation counts and fail migration verification on duplicate mappings.
3. Do not guess postal locality from free-text legacy addresses or postal-code arrays. Mark physical legacy rows `LEGACY_UNVERIFIED`, preserve their existing display, and require PIN verification on the next edit. Mark abstract nodes without addresses `NOT_APPLICABLE`.
4. Convert geofences only when the existing object matches a supported shape; otherwise retain a read-only legacy representation and require correction before the next edit/deactivation-reassignment that depends on it.
5. Create employee region coverage from the unambiguous region ancestor of each active home node when one exists; leave explicit reconciliation items when zero or multiple valid ancestors exist.
6. Verify clean-database migration, upgrade from the pre-MST-01 schema, RLS inventory, closure/scope reconciliation, duplicate linked memberships, legacy counts, and rollback of an intentionally failed backfill transaction.
7. Reversal means deploying code that ignores new nullable fields/tables; migrations are not destructively rolled back. Once canonical address/scope writes begin, retain new data and ship a forward correction.

## Domain rules and calculations

- Hierarchy descendants are determined from closure rows at the transaction snapshot. Moving a subtree updates all affected ancestor/descendant closure pairs atomically; a node cannot move below itself/its descendants or under an invalid/inactive parent.
- Cascading scope is computed from the canonical organization node and its scope ancestor. A linked employee membership receives only the intersection of role capabilities, active FND-02 grants, employee home/region/operational coverage and explicit policy restrictions. Reassignment never broadens capability; it changes resource coverage and increments access context version so stale sessions refresh.
- Employee region coverage is explicit where selected. Home-node ancestry provides an implicit minimum region for operational ownership but does not create hidden access beyond FND-02 grants.
- Deactivation preview counts and lists the exact scoped impacts: descendants, direct reports, employees, linked memberships/grants, assignments, clients, client locations, vendors, open indents/allocations/trips, and escalation/alert routes where applicable. Summary counts must equal the drill-down rows at the same snapshot/as-of time.
- Normal deactivation is permitted with zero impact or a complete valid replacement plan. Replacement copies/retargets active responsibilities with the original effective history closed at the transaction instant. Historical records retain the original owner snapshot; only current/open ownership changes.
- Exception deactivation requires `masters.exception`, reason of 10–1000 characters, an active review owner, review-by date no more than 30 days ahead, and an immutable impact snapshot. It emits an alert immediately and daily deduplicated reminders until resolved/expired.
- Reports use current active ranges at `asOf`; an “unowned” record is active/open and lacks an active authorized employee assignment and active escalation fallback at that instant. Counts must reconcile with permission-scoped detail IDs.
- All creates, edits, moves, bulk assignments, scope synchronizations and deactivations require an idempotency key. The stored request hash includes actor tenant/membership, route aggregate and canonical body.

## Reports and alerts

- **Organization tree report:** visible nodes by type/state/root with descendant, employee, client-location, assignment and open-record counts. Each count drills to the exact permission-scoped rows used in the formula. `total = sum(group counts)` for mutually exclusive node-state/type groupings, and `asOf`/freshness is displayed.
- **Ownership coverage report:** active clients, client locations, vendors and open operational records grouped by current employee/manager; separate unowned and inactive-owner groups. A record counts once under its canonical current owner, and every summary provides detail IDs at the same snapshot.
- **Exceptions report:** open/expired/resolved deactivation exceptions with target, impact count, review owner, review-by date and resolution. Sensitive audit data follows FND-02 masking.
- Exports use the same server filters, authorization and snapshot as the on-screen report, contain human-readable codes/names rather than raw reference IDs, include generated-at/as-of metadata, and create audit evidence.
- Alerts: `ownership.unowned`, `ownership.inactive_owner`, `ownership.no_escalation`, and `master.deactivation_exception_due`. Recipients are active Tenant Owners plus configured scoped managers/escalation roles who are authorized to see the resource. An alert is not sent to an inactive owner.
- Deduplication key is tenant + alert type + resource type/id (+ exception ID where relevant). Re-evaluation updates the existing open alert instead of creating noise. Reassignment/exception resolution closes the condition; acknowledgement alone does not resolve it. Failed evaluations retry through the existing PostgreSQL worker lease and appear in operational health without falsely marking success.

## Audit, observability, and security

- Immutable audit records capture actor, tenant, impersonation context, action, target, correlation/request ID, reason, safe before/after, impact snapshot ID, replacement/exception references and timestamp for create/edit/move/assignment/scope/deactivation/export actions.
- Employee contact details are PII. Lists show only what the actor needs; audit/report payloads avoid full mobile/email unless the existing sensitive-read policy permits it. Activation tokens, session/MFA data and secrets never appear in MST-01 APIs/logs.
- Metrics/logs include request count/latency/error by stable route/action/code; postal lookup outcomes; hierarchy move duration/conflict; impact category counts; reassignment rollback/success; scope-sync duration/failure; orphan alert evaluation lag; report freshness; and correlation ID. Do not put tenant names, employee names, emails, mobiles, addresses, coordinates or tokens in metric labels/log messages.
- PostgreSQL constraints, forced RLS and server service/query authorization are mandatory defense in depth. Direct API calls, guessed IDs, selector endpoints, reports, exports and alert actions receive the same enforcement as the UI.
- Scope-changing writes increment/revoke the affected access context/session version according to FND-02 so an already-open session cannot continue with stale breadth. Failed scope synchronization rolls back the master write.
- Failure recovery is retry-safe through idempotency records and atomic transactions. The alert evaluator and event projector claim work with PostgreSQL locks/leases and record attempts; no Redis/queue/container is introduced.
