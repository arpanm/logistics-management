# UI-MODERNIZATION — Responsive interface and rich demo-data test plan

**Plan status:** Detailed
**Overall test status:** Implemented / Not Run — focused shell, Control Tower, responsive-layout, pagination and demo-manifest assertions were authored; no test was executed in this batch
**Related scope:** Shared application shell and design system, `CTL-01`, `DEMO-DATA`, representative tables/reports across Operations, Finance, Masters, Access and Platform

This plan verifies that the modernization is usable rather than merely restyled: labels and values remain contained, controls do not collide, dense data is legible, mobile journeys preserve the same meaning and actions, and Control Tower totals still reconcile to canonical tenant-scoped records. It supplements the existing `OFC-CTL-*`, `OFC-A11Y-E2E-032` and `E2E-DEMO-*` cases; it does not change their recorded status. Planning did not authorize test execution.

## Deterministic fixtures

- Use the real locally deployed Next.js frontend, NestJS backend and shared PostgreSQL test schema. Do not use production data, browser route interception, mocked business APIs or direct writes to production tables.
- Create the versioned `2026.09.2` showcase through the supported demo bootstrap with a fixed `2026-08-31T06:30:00.000Z` anchor, `Asia/Kolkata`, `en-IN` and `INR`. Natural keys, UUID namespace, amounts, times and expected aggregates are versioned and repeatable.
- Tenant A contains an owner, traffic executive, finance maker, finance checker, collections user, auditor, client viewer and vendor owner. Tenant B mirrors selected human references and long names so tenant derivation and non-leaking searches are provable.
- Tenant A showcase baseline: 4 clients, 10 locations, 5 vendors, 12 vehicles, 10 drivers, 36 indents, 24 allocations, 18 trips, 14 POD tasks, 18 client invoices, 8 receipts, 14 vendor bills, 5 payment runs and 12 alerts. Each Control Tower lens exposes at least 10 scoped records. A separate high-volume/load profile remains planned rather than inflating the client-demo seed.
- Cover each material lifecycle and boundary: Green/Yellow/Red placement at 24/48 hours, POD at 7/15 days, collection at 30/45/90 days, active/delayed/GPS-silent trips, draft/approval/due/overdue/disputed/blocked/paid vendor bills, partial receipts and compensating reversals. Money remains integer minor units.
- Include adversarial but valid display strings: 80-character client/vendor names, 64-character references, multi-word location names, unbroken IDs, negative/zero/12-digit amounts, masked values, empty optional values and Unicode text. Invalid fixture variants exceed the documented maximum by one character and use unsupported enum/filter IDs.
- Expected fixture artifacts include a manifest of row counts, per-lens KPI totals, ageing totals, permitted field projections and CSV hashes/rows. Independent reconciliation queries derive expectations from canonical rows rather than UI response summaries.
- Keep showcase credentials out of source and logs. Fixture actors authenticate through the established test helpers; every mutation uses a per-test namespace/idempotency key and waits for its response plus persisted projection.

## Layout assertion contract

`expectNoPageOverflow` alone is insufficient. The planned shared helper must report the offending selector, viewport and rectangles and apply these deterministic rules after the named loading/data state is observable:

1. `documentElement.scrollWidth <= documentElement.clientWidth`; page-level horizontal scroll is always a failure.
2. Each visible target has finite positive dimensions and stays within the viewport or its nearest explicitly allow-listed scroll owner.
3. For named peer groups (tab labels, toolbar controls, card label/value/badge, table headers/cells/actions, feedback and dialog controls), non-ancestor rectangles must not overlap by more than a one-pixel rounding tolerance.
4. A scroll owner has `scrollWidth > clientWidth` only when its accessible label/instructions identify the region; first and last columns/actions remain reachable by keyboard and pointer.
5. Text must wrap, break safely or use intentional ellipsis. Clipping is permitted only when the full value is programmatically available and row/field association remains unambiguous.
6. Sticky navigation/header/footer elements must not cover the focused control, dialog, toast, first/last table row or anchored heading after scroll.

Visual snapshots complement these geometry/semantic assertions; they do not replace them.

## Playwright journeys and waits

- Extend `tests/e2e/control-tower-workbench.spec.ts` for `UIM-E2E-002` through `006`, `008` and `UIM-AUTH-*`; add a focused `tests/e2e/ui-modernization.spec.ts` for global shell, cross-module responsive and visual cases.
- Add a versioned fixture helper such as `tests/fixtures/ui-volume.ts`; it may use supported setup/bootstrap APIs and test-only fault/clock controls, never production records or browser-only business calculations.
- Use semantic role/label locators. Wait for the relevant response and observable heading/status/row count, download event, focus target or persisted API projection. Never use `waitForTimeout`, arbitrary polling intervals or animation-duration sleeps.
- Run each visual journey in Chromium with deterministic fonts/locale/clock and explicit viewport. Functional mobile assertions also run in the existing `mobile-chromium` project; do not infer mobile success from desktop screenshots.
- Failure cases compare canonical row, audit and outbox counts before/after. Reconciliation reads the supported API and an independent test query at the same fixture `asOf`.

## Critical risks

- A fluid grid can avoid page overflow while labels, values and badges still collide inside a card; geometry must be asserted at element level.
- Making tables horizontally scrollable can conceal the row identity or action column and create an unusable mobile experience despite passing page-width checks.
- Responsive card alternatives can accidentally expose hidden financial/PII fields or omit actions and meaning available on desktop.
- Screenshot-only tests can be unstable across fonts/animations and can miss semantic regressions; deterministic state and functional assertions are mandatory.
- Large demo volume can conceal incorrect denormalized totals, duplicate values or tenant leakage; every displayed aggregate needs a canonical reconciliation oracle.
- Enrichment reruns or concurrency can duplicate ledgers/audit/events or overwrite a user's evolving demonstration state.
- A modern visual redesign can reduce contrast, keyboard visibility, information density or report scanability even when it appears cleaner.
